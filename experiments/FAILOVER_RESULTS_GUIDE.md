# StableShots QPU-Failover Results Guide

This guide explains how to interpret, filter, combine, and visualize the CSV files and plots generated by the failover experiment branch.

The raw experiment data are written under **results/qpu_failover/raw/**. Derived summaries are written under **results/qpu_failover/analysis/**. Figures are written under **results/qpu_failover/plots/**.

Do not manually edit the raw CSV files. If analysis logic changes, rerun **experiments/analyze_failover_results.py** so derived outputs remain reproducible.

## 1. Run manifest

**results/qpu_failover/run_manifest.json**

This is the provenance record for the experiment run.

It contains:

- the experiment name;
- configuration path;
- start and end timestamps;
- StableShots configuration identifier;
- selected run mode;
- a full copy of the JSON experiment configuration.

Use this file first when comparing result folders. Two result directories should not be considered directly comparable until their manifests have been checked.

## 2. qpu_references.csv

**results/qpu_failover/raw/qpu_references.csv**

One row corresponds to one:

\[
(\text{circuit},\text{backend})
\]

high-shot noisy reference.

Important columns:

| Column | Meaning |
| --- | --- |
| circuit_key | Algorithm-size circuit identifier |
| algorithm | Circuit family |
| size | Circuit size |
| backend | Noisy QPU/backend |
| reference_tvd_to_aer | TVD between the backend high-shot reference and the high-shot Aer reference |

This table defines the oracle reliability ordering used only for experimental replacement conditions.

For a given circuit, lower reference_tvd_to_aer means the backend is closer to Aer.

Do not interpret this as an online scheduling signal. It is post-hoc ground truth used to define favorable and adverse replacement conditions.

## 3. no_failure_runs.csv

**results/qpu_failover/raw/no_failure_runs.csv**

One row corresponds to ordinary StableShots on one circuit/backend with no injected failure.

Important columns:

| Column | Meaning |
| --- | --- |
| circuit_key | Algorithm-size identifier |
| backend | QPU/backend |
| shots | StableShots stopping shot count |
| final_tvd_to_aer | Final TVD to Aer |
| target_violation | Whether final TVD exceeds the configured target |
| stop_reason | Stable or max-budget stop |
| last_stability_tvd | Last StableShots marginal TVD |

This table is the counterfactual baseline for the single-failure study.

The value in shots is the source-specific \(N_0\) used to place failures at 10%, 25%, 50%, 75%, and 90% of the execution's own no-failure stopping point.

## 4. fixed_shot_runs.csv

**results/qpu_failover/raw/fixed_shot_runs.csv**

One row corresponds to one fixed-shot budget on one circuit/backend.

Use this table to retain continuity with the original StableShots evaluation.

Typical questions:

- How does no-failure StableShots compare to 1k, 5k, 10k, or 20k fixed budgets?
- Does a failover policy still outperform a conservative fixed budget in shot use?
- Is a policy's final TVD competitive with a fixed-shot baseline?

## 5. single_failure_runs.csv

**results/qpu_failover/raw/single_failure_runs.csv**

This is the main raw dataset.

Each row is one fully specified directed handoff experiment:

\[
(\text{circuit},A,B,\tau,\text{policy}).
\]

### Identity columns

| Column | Meaning |
| --- | --- |
| circuit_key | Algorithm-size circuit identifier |
| algorithm | Circuit family |
| size | Circuit size |
| source_backend | QPU active before failure |
| target_backend | Replacement QPU |
| policy | Recovery/baseline policy |
| failure_fraction | Fraction of source no-failure stop at which failure was injected |

### Failure timing columns

| Column | Meaning |
| --- | --- |
| failure_shots | Physical source-QPU shots executed before failure |
| no_failure_shots | Counterfactual source-QPU no-failure stopping shots |
| post_failure_shots | Physical replacement-QPU shots after failure |
| target_batches_consumed | Number of replacement-QPU batches consumed |

failure_fraction is the controlled experimental variable. failure_shots is the realized batch-aligned location.

### Resource columns

| Column | Meaning |
| --- | --- |
| physical_shots_total | Every physically executed shot, including later-discarded evidence |
| effective_retained_shots | Effective count mass in the final estimator |
| target_evidence_share | Derived analysis field: post-failure replacement-QPU shots divided by final effective count mass |
| retained_source_evidence_share | Derived analysis field: one minus target_evidence_share |
| discarded_or_downweighted_shots | physical_shots_total minus effective retained evidence |
| shot_overhead_vs_no_failure | Physical shots minus source no-failure StableShots shots |
| shot_ratio_vs_no_failure | Physical shots divided by source no-failure shots |

For full restart, discarded_or_downweighted_shots includes source shots discarded at handoff.

For decay policies it includes the portion of old evidence removed by weighting.

For naive continuation, controller reset, and epoch-local output retention, it is normally zero.

### Accuracy columns

| Column | Meaning |
| --- | --- |
| final_tvd_to_aer | Primary accuracy metric |
| no_failure_tvd_to_aer | Source-QPU counterfactual StableShots TVD |
| delta_tvd_vs_no_failure | final TVD minus no-failure TVD |
| target_violation | Whether final TVD exceeds configured target |
| source_tvd_to_aer | High-shot source-QPU error |
| target_tvd_to_aer | High-shot replacement-QPU error |
| quality_change | target error minus source error |
| pair_reference_tvd | High-shot source-target distribution shift |

Interpret quality_change as:

\[
\text{quality_change}<0
\]

means the handoff moved to a QPU closer to Aer.

\[
\text{quality_change}>0
\]

means the handoff moved to a QPU farther from Aer.

pair_reference_tvd is symmetric, but the row remains directional because source and target quality differ.

### StableShots columns

| Column | Meaning |
| --- | --- |
| stop_reason | Stable, recovery budget, or input exhaustion |
| stability_checks | Number of post-handoff checks made by the active controller |
| last_stability_tvd | Last marginal TVD seen by the active controller |

The meaning of the active controller depends on policy. For epoch-local recovery it sees only the replacement epoch. For controller-reset/fixed-decay/shift-aware recovery it sees a reset controller with the configured retained evidence.

### Shift-aware columns

Only shift-aware rows contain finite values for all of these fields.

| Column | Meaning |
| --- | --- |
| shift_handoff_mean_tvd | Mean TVD between equal-size bootstrap old samples and actual new-QPU probe |
| shift_null_mean_tvd | Mean old-vs-old TVD expected from finite sampling alone |
| shift_corrected_tvd | max(0, handoff mean minus null mean) |
| shift_null_percentile | Location of handoff mean relative to the null bootstrap distribution |
| adaptive_lambda | Retention weight selected from the observed shift |

The default adaptive rule is:

\[
\lambda
=
\min
\left(
1,
\frac{\bar D_{\mathrm{null}}}
{\max(\bar D_{\mathrm{handoff}},\varepsilon)}
\right).
\]

### Useful filters

To isolate late failures:

~~~python
late = df[df["failure_fraction"] >= 0.75]
~~~

To isolate degrading handoffs:

~~~python
worse = df[df["quality_change"] > 0]
~~~

To isolate improving handoffs:

~~~python
better = df[df["quality_change"] < 0]
~~~

To compare only one directed pair:

~~~python
pair = df[
    (df["source_backend"] == "fake_kyiv")
    & (df["target_backend"] == "fake_marrakesh")
]
~~~

To compare recovery methods at one failure location:

~~~python
mid = df[df["failure_fraction"] == 0.50]
~~~

## 6. single_failure_summary.csv

**results/qpu_failover/analysis/single_failure_summary.csv**

This is the main high-level policy table.

Rows are grouped by:

- policy;
- failure_fraction.

For each metric it reports:

- median;
- mean;
- 25th percentile;
- 75th percentile;
- 95th percentile;
- bootstrap confidence interval around the median.

It also reports target_violation_rate.

Use this table to answer:

- Which recovery policies degrade most at late failures?
- Which policies require the most additional physical shots?
- Does decay reduce target violations compared with naive continuation?
- Does shift-aware decay approach the best fixed lambda without knowing the true pair shift?

## 7. handoff_pair_summary.csv

**results/qpu_failover/analysis/handoff_pair_summary.csv**

Rows are grouped by:

\[
(\text{source},\text{target},\text{policy},\tau).
\]

This is the main table for directed QPU-pair analysis.

Use it together with the heatmaps to identify:

- consistently difficult handoffs;
- asymmetric quality effects;
- pairs where a recovery method is robust across failure times;
- pairs where replacement accuracy and source-target shift tell different stories.

Do not collapse source and target into an unordered pair if analyzing quality_change; direction is essential.

## 8. handoff_predictor_correlations.csv

**results/qpu_failover/analysis/handoff_predictor_correlations.csv**

For every policy and failure fraction, this file contains Spearman correlations between explanatory variables and recovery outcomes.

Predictors:

- pair_reference_tvd;
- target_tvd_to_aer;
- quality_change;
- source_tvd_to_aer.

Outcomes:

- final_tvd_to_aer;
- delta_tvd_vs_no_failure;
- post_failure_shots;
- shot_overhead_vs_no_failure.

Important interpretation:

A strong correlation between pair_reference_tvd and recovery degradation suggests that **handoff discontinuity** matters independently of replacement quality.

A strong correlation between target_tvd_to_aer and final error suggests absolute replacement quality dominates.

A strong correlation with quality_change suggests the direction of quality movement—better to worse or worse to better—is central.

Correlation does not establish causal importance by itself; it is an explanatory analysis of the controlled pair experiments.

## 9. decay_sensitivity.csv

**results/qpu_failover/analysis/decay_sensitivity.csv**

This file contains only:

- fixed-decay policies;
- shift-aware decay.

It is grouped by policy and failure fraction.

Use it to answer:

- Is there a universally strong fixed lambda?
- Does the best fixed lambda depend on failure timing?
- Does shift-aware decay track the fixed-lambda frontier without oracle pair information?
- Does aggressive forgetting help late improving handoffs but hurt degrading handoffs?

A useful follow-up analysis is to further split fixed-decay rows by sign of quality_change.

## 10. oracle_replacement_runs.csv

**results/qpu_failover/analysis/oracle_replacement_runs.csv**

This is not a new simulation result. It is a deterministic selection from the exhaustive directed-pair table.

Additional columns:

| Column | Meaning |
| --- | --- |
| replacement_condition | most reliable remaining, least reliable remaining, or random remaining |
| replacement_repetition | 0 for deterministic conditions, repetition ID for random |
| selected_target_tvd_to_aer | Oracle target error of the chosen replacement |

This file makes replacement selection explicitly an **experimental condition**, not a scheduling algorithm.

Use it to study sensitivity to favorable/adverse/random replacement choices.

## 11. oracle_replacement_summary.csv

**results/qpu_failover/analysis/oracle_replacement_summary.csv**

Rows are grouped by:

- replacement_condition;
- policy;
- failure_fraction.

This is the appropriate table for statements such as:

- how much performance changes between favorable and adverse replacements;
- whether a recovery policy is robust to replacement quality;
- whether random replacement lies between the two oracle extremes.

Avoid statements implying that the experiment proposes an online mechanism for discovering the oracle ranking.

## 12. multi_failure_runs.csv

**results/qpu_failover/raw/multi_failure_runs.csv**

This is the deterministic repeated-failure stress test.

Important columns:

| Column | Meaning |
| --- | --- |
| sequence_condition | ascending reliability, descending reliability, or random |
| sequence | JSON array of QPUs in failover order |
| planned_failures | Number of scheduled failures |
| actual_failures | Number that occurred before stopping |
| failure_targets | Cumulative physical-shot targets for scheduled failures |
| epoch_physical_shots | Physical shots spent in each realized QPU epoch |
| handoff_lambdas | Retention lambdas used at handoffs |
| handoff_corrected_shifts | Shift-aware corrected TVDs |
| final_tvd_to_aer | Final accuracy |
| physical_shots_total | Total resource cost |

Because a run may stop before the second planned failure, always inspect actual_failures before comparing multi-failure rows.

Treat the three sequence conditions as separate experiments for reporting purposes:

1. **ascending_reliability** - aggregate only across circuits/repetitions in the ascending scenario;
2. **descending_reliability** - aggregate only across circuits/repetitions in the descending scenario;
3. **random** - aggregate only across the random permutations and circuits in the random scenario.

Do **not** compute or report a pooled multi-failure median across these three scenarios. `multi_failure_summary.csv` keeps `sequence_condition` in every group, while `multi_failure_by_actual_failures.csv` additionally conditions on realized failure count.

## 13. multi_failure_summary.csv

**results/qpu_failover/analysis/multi_failure_summary.csv**

Use this file only after the single-failure mechanism is understood.

Its role is to test whether conclusions compose:

- Does a recovery method remain effective after more than one handoff?
- Does accumulated decay eventually discard too much useful evidence?
- Does naive continuation become more problematic under multiple distribution changes?
- Are worst-to-best and best-to-worst sequences asymmetric?

The repeated-failure study is a robustness experiment, not the primary causal analysis.

## 14. stochastic_failure_runs.csv

**results/qpu_failover/raw/stochastic_failure_runs.csv**

Each row is one Monte Carlo run under a per-batch failure probability.

Important columns:

| Column | Meaning |
| --- | --- |
| failure_probability_per_batch | Bernoulli hazard after each completed batch |
| sequence_condition | Backend ordering rule |
| repetition | Monte Carlo repetition |
| actual_failures | Realized failures |
| physical_shots_total | Total resource cost |
| final_tvd_to_aer | Final accuracy |
| target_violation | Accuracy-target violation |
| handoff_lambdas | Shift-aware/fixed decay history when applicable |

Some runs may have zero failures, especially at low failure probabilities. Do not interpret them as recovery events without conditioning on actual_failures.

## 15. stochastic_failure_summary.csv

**results/qpu_failover/analysis/stochastic_failure_summary.csv**

Grouped by:

- sequence condition;
- per-batch failure probability;
- policy.

The scenario boundary is mandatory: ascending, descending, and random are discussed separately and are never pooled. `stochastic_failure_by_actual_failures.csv` provides the stricter view conditioned on realized failure count.

Use these tables to test whether conclusions from controlled failure locations remain visible under random timing within each replacement-order scenario.

It should not replace the fixed-location study because random hazards mix together:

- failure timing;
- number of failures;
- source QPU;
- target QPU;
- amount of retained progress.

## 16. Plots

### failure_fraction_accuracy.png

Shows median final TVD to Aer as failure location changes.

Read left to right as progressively later failures.

Look for:

- policies that deteriorate at 75–90%;
- policies insensitive to failure timing;
- crossovers between restart and retention policies.

### failure_fraction_shot_overhead.png

Shows median physical-shot overhead relative to no-failure StableShots.

This should be interpreted jointly with the accuracy plot.

A policy that achieves excellent TVD by consuming far more shots is not equivalent to a recovery policy that preserves work efficiently.

### oracle_replacement_accuracy.png

Compares final TVD under:

- most reliable remaining;
- least reliable remaining;
- random remaining.

Use it to quantify how much recovery conclusions depend on replacement quality.

### oracle_replacement_shot_overhead.png

Same replacement conditions, but for physical-shot overhead.

This can reveal situations where the most accurate replacement does not converge fastest.

### shift_aware_lambda_response.png

Scatter plot of:

\[
S_{\mathrm{corrected}}
\]

against

\[
\lambda.
\]

It verifies that the adaptive policy is responding monotonically to detected handoff shift.

Points near \(\lambda=1\) correspond to handoffs that look similar to ordinary finite-shot variation. Lower lambdas indicate stronger detected change.

### handoff_heatmaps/

Each heatmap has:

- source QPU on rows;
- target QPU on columns.

There are separate heatmaps for selected policies and metrics.

Diagonal cells are absent because a failure never replaces a QPU with itself.

These figures are useful for spotting pair-specific structure that disappears in aggregate summaries.

### multi_failure_accuracy_<scenario>.png

Three separate accuracy figures are emitted:

- `multi_failure_accuracy_ascending_reliability.png`;
- `multi_failure_accuracy_descending_reliability.png`;
- `multi_failure_accuracy_random.png`.

Matching `multi_failure_shots_<scenario>.png` figures report physical-shot cost. No cross-scenario curve is produced.

### stochastic_failure_accuracy_<scenario>.png

Three separate accuracy figures are emitted for ascending, descending, and random sequence conditions, with matching `stochastic_failure_shots_<scenario>.png` cost figures.

Each plot aggregates only inside its named scenario. This is the final robustness view rather than the main mechanistic result.

## 17. Recommended analysis order

A defensible analysis workflow is:

1. inspect run_manifest.json;
2. inspect qpu_references.csv to understand backend-quality spread;
3. inspect no_failure_summary.csv and fixed_shot_summary.csv;
4. analyze single_failure_summary.csv;
5. inspect failure-location plots;
6. analyze handoff_pair_summary.csv and pair heatmaps;
7. inspect handoff_predictor_correlations.csv;
8. analyze decay_sensitivity.csv;
9. compare oracle replacement conditions;
10. inspect multi-failure and stochastic-failure robustness in three separate subsections: ascending reliability, descending reliability, and random.

Never collapse these three robustness scenarios into one aggregate result. This order and separation prevent repeated-failure complexity and opposite migration directions from obscuring the single-handoff mechanism.

## 18. Statistical reporting

The analysis script reports bootstrap confidence intervals for medians because the distributions of TVD and shot counts can be skewed. Aggregate confidence intervals are clustered by `circuit_key`: a bootstrap replicate resamples circuits and keeps the repeated source-target, policy, failure-location, and random-repetition observations associated with each selected circuit together.

For paper tables, prefer at least:

- median;
- interquartile range;
- 95% bootstrap confidence interval;
- target-violation rate.

Means can be reported as supplementary statistics but should not replace robust summaries.

When comparing policies on the same circuit/source/target/failure location, exploit the paired design in any later formal significance test. The current analysis script focuses on descriptive/bootstrap summaries and correlation analysis rather than adding a large battery of hypothesis tests by default.

## 19. Comparing physical and effective shots

Do not confuse these quantities.

**physical_shots_total** answers:

> How many quantum measurements were actually executed and paid for?

**effective_retained_shots** answers:

> How much count mass remains in the final weighted estimator?

For decay, the second can be non-integer.

A policy must never claim resource savings merely because it downweighted evidence after those shots had already been executed.

## 20. Interpreting negative delta TVD

A negative **delta_tvd_vs_no_failure** is possible and meaningful.

It means:

\[
\mathrm{TVD}_{\mathrm{failure}}
<
\mathrm{TVD}_{\mathrm{no\ failure}}.
\]

The failure path ended closer to Aer than the source-QPU no-failure counterfactual.

This can happen when a poor initial QPU fails and is replaced by a better one.

Therefore failure resilience should not be described only as "damage minimization." Migration can also change execution quality favorably.

## 21. Interpreting epoch-local recovery

Epoch-local StableShots intentionally uses different distributions for:

- stopping;
- final output.

The controller sees only the replacement epoch, while the final output contains pre- and post-failure measurements.

This policy should primarily be treated as an ablation answering:

> Is it useful to remove historical measurements from the stopping decision without removing them from the final estimator?

If it performs poorly, that is evidence that stopping semantics and final-estimator semantics should remain aligned.

## 22. Interpreting shift-aware decay

Shift-aware decay is not allowed to inspect:

- Aer ground truth;
- high-shot source/target reference TVD;
- oracle reliability ranking.

Its only handoff signal is:

1. the current cumulative empirical distribution;
2. an ordinary probe from the replacement QPU;
3. bootstrap resampling of the old cumulative distribution.

This distinction is important when discussing deployability.

The oracle replacement conditions are outside the recovery policy; the shift-aware policy remains observational.

## 23. Regenerating analysis

After any analysis-script change:

~~~bash
uv run python experiments/analyze_failover_results.py \
  --config experiments/failover_config.json
~~~

The script overwrites derived CSVs and plots but leaves raw CSVs untouched.

## 24. Changing experiment scale

All scale changes belong in **experiments/failover_config.json**.

Common changes:

- fewer algorithms/sizes for smoke testing;
- different fixed failure fractions;
- different fixed decay lambdas;
- different probe size;
- more bootstrap repetitions;
- more random replacement repetitions;
- disabling multi-failure or stochastic experiments;
- changing output_dir to preserve an earlier run.

For a smoke test, use a separate output directory rather than writing into a full experiment directory.

## 25. Archiving a completed run

For a paper artifact, archive together:

- failover_config.json;
- run_manifest.json;
- raw/;
- analysis/;
- plots/;
- the exact Git commit/branch identifier.

The two Markdown guides describe semantics, but the manifest and Git revision provide the actual provenance required to reproduce the run.


## Automatic result publication

The experiment configuration contains a **git_publish** block. With the default research configuration, automatic publication is enabled only for branch **research/qpu-failover-stableshots**.

After a successful experiment run, the experiment launcher stages, commits, and pushes only:

- the generated run manifest;
- the configured raw-results directory.

After a successful analysis run, the analysis script separately stages, commits, and pushes only:

- the generated analysis CSV directory;
- the generated plots directory.

The scripts refuse to publish if the currently checked-out Git branch does not exactly match the configured branch. Unrelated repository files are not staged or committed.

Automatic publication can be disabled without editing the configuration by setting:

~~~bash
STABLESHOTS_DISABLE_AUTO_PUSH=1
~~~

The GitHub Actions smoke test sets this variable and also disables publication in its temporary smoke configuration, so CI artifacts are uploaded to the workflow rather than committed to the research branch.


## Handoff magnitude, evidence composition, and restart-normalized response

The primary single-failure analysis avoids the globally signed median Delta TVD because improving and degrading directed handoffs can cancel.

For every single-failure row the analysis adds:

- **abs_delta_tvd** - absolute TVD change relative to the matched no-failure source run;
- **handoff_direction** - improving or degrading according to independently sampled backend-quality references;
- **restart_delta_tvd** - matched full-restart TVD change;
- **target_evidence_share**:
  [
  w_B = rac{N_{mathrm{post}}}{N_{mathrm{effective}}};
  ]
- **handoff_transfer_coeff**, interpreted in the paper as the **restart-normalized handoff response**:
  [
  H_p = rac{Delta TVD_p}{Delta TVD_{mathrm{restart}}}.
  ]

The default denominator guard is

[
|Delta TVD_{mathrm{restart}}| ge 0.01.
]

Restart is the zero-retained-history reference, not the accuracy optimum and not an upper bound. Do not describe (H) as the literal fraction of the new QPU distribution transferred; TVD need not vary linearly under mixtures.

Use **evidence_share_correlations.csv** to test the history-inertia mechanism directly. It reports the within-policy/failure-location association between replacement evidence share (w_B) and restart-normalized response (H), plus the median residual (H-w_B).

The main single-handoff reporting set is therefore:

1. signed Delta TVD for direction;
2. absolute Delta TVD for realized handoff impact;
3. target evidence share (w_B) for the mechanism;
4. restart-normalized response (H) for the statistical consequence;
5. physical-shot overhead for cost.

The threshold sensitivity table remains at 0.005, 0.01, and 0.02. Values of (H) outside ([0,1]) are retained and reported rather than clipped.

### Robustness discussion structure

The repeated- and stochastic-failure discussion must be written in exactly three scenario-level parts:

1. **Ascending reliability**
2. **Descending reliability**
3. **Random**

Aggregate within each scenario only. Do not average, pool, or draw a single headline robustness statistic across the three scenarios. This separation is required because the scenarios encode qualitatively different replacement trajectories and can otherwise recreate the same cancellation problem seen in globally signed single-handoff Delta TVD.

### Reference-sample independence

New experiment runs use a dedicated `backend_reference_seed` distinct from `sampling_seed`, so the samples used to classify backend quality are separate from the execution samples used to evaluate policies. Changing this seed or adopting the independent-reference design requires regenerating the raw experiment files; rerunning the analysis alone cannot retrofit independence into an older raw dataset.
